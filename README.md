# JMAP Gateway

A Go gateway for existing IMAP accounts and their authenticated SMTP submission services. It exposes a limited [JMAP Core (RFC 8620)](https://www.rfc-editor.org/rfc/rfc8620.html) and [JMAP Mail (RFC 8621)](https://www.rfc-editor.org/rfc/rfc8621.html) API over HTTPS. This release targets the client flow below. General-purpose clients may require additional JMAP methods.

The client sends JMAP JSON over HTTPS. The gateway translates mailbox discovery, querying, reading, draft creation, and seen-state updates to IMAP. It translates submission to SMTP. The recipient's mail server owns delivery. The separate emulator provides a second target for the same acceptance client.

## Run

Build on Linux with Go 1.25 or later.

```sh
go test ./...
mkdir -p .local
go build -o .local/jmap-gateway ./cmd/jmap-gateway
```

To expose a Drafts role, configure the exact IMAP path or omit `DraftsMailbox` to discover it via IMAP SPECIAL-USE. Draft creation accepts one writable mailbox and requires UIDPLUS or IMAP4rev2 with an APPENDUID response.

Save this example as `.local/config.json` with mode `0600`. Replace all deployment values. Use a random bearer token of at least 32 characters, for example one generated by `openssl rand -hex 32`.

```json
{
  "Listen": "127.0.0.1:8443",
  "PublicOrigin": "https://jmap.example.org",
  "TLSCert": "/etc/jmap-gateway/fullchain.pem",
  "TLSKey": "/etc/jmap-gateway/privkey.pem",
  "StateDir": "/var/lib/jmap-gateway",
  "AccountID": "primary",
  "Token": "replace-with-a-random-bearer-token",
  "IdentityName": "Example Sender",
  "IdentityEmail": "sender@example.org",
  "DraftsMailbox": "Drafts",
  "IMAP": {
    "Address": "imap.example.org:993",
    "Username": "sender@example.org",
    "Password": "replace-with-the-imap-password",
    "Mode": "tls"
  },
  "SMTP": {
    "Address": "smtp.example.org:587",
    "Username": "sender@example.org",
    "Password": "replace-with-the-smtp-password",
    "Mode": "starttls"
  }
}
```

```sh
.local/jmap-gateway -config .local/config.json
```

Set `Listen` to the HTTPS bind address for your deployment. The advertised origin comes from `PublicOrigin`. The configured origin must route to the gateway. When using a reverse proxy, preserve the Authorization header and use HTTPS to the gateway. The listener and each upstream require TLS 1.2 or newer. SMTP supports `starttls` and implicit `tls`, with SASL PLAIN over TLS. Both upstreams verify the certificate and hostname. An optional `CAFile` on either upstream replaces its system trust roots with the specified PEM trust bundle.

Use a dedicated service user and configuration for each bearer authorization group. Give each configured account its own persistent state directory. The state directory must have mode `0700`. Keep `AccountID` stable for the same upstream account. Clients authenticate using `Authorization: Bearer <token>`. Gateway responses use fixed error descriptions and omit upstream diagnostics, credentials, and message bodies from logs.

## Additional accounts

The top-level account remains primary. Optionally add up to five entries under `AdditionalAccounts`, each with a distinct `AccountID` and private `StateDir`, its own `IMAP` and `SMTP` settings and `IdentityEmail`, and optional `IdentityName`, `DraftsMailbox`, `MailboxMetadataVendor`, `SMTPDeliveryNotifications`, `SMTPDeliveryReportMailbox`, `ManageSieve`, and `CalDAV`. The configured bearer token grants access to every account listed in that configuration. Keep accounts that require separate authentication in separate gateway instances.

Clients discover the attached accounts in the session and select one using `accountId`. Uploads, downloads, synchronization state, SMTP submission records, and upstream credentials are scoped to each account. EventSource and confirmed HTTP push subscriptions can report changes in any account in the session.

Use `Blob/copy` for an existing upload, message, or MIME part. The target copy counts toward its temporary blob quota. Use `Email/copy` with a target mailbox ID to preserve the stored message bytes and optionally replace keywords or received date. Set `ifFromInState` and `ifInState` to require specific source and destination states. With `onSuccessDestroyOriginal`, a separate implicit `Email/set` response reports whether the successfully copied originals were removed. Use `destroyFromIfInState` to condition that step on the source state. [Blob/copy](https://www.rfc-editor.org/rfc/rfc8620.html#section-6.3) · [Email/copy](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.7)

## Sender identities

`Identity/get`, `Identity/changes` and `Identity/set` expose per-account sender profiles. The primary identity uses the configured `IdentityEmail` and has a fixed ID. Optionally set `IdentityAliases` to explicit sender addresses the account’s SMTP server permits. Configure aliases separately for each account. JMAP clients can create profiles for authorized addresses, choose display names, manage Reply-To and Bcc defaults, and store plain-text and HTML signatures. Clients apply those defaults when composing an Email.

A profile’s email address is immutable. The primary profile cannot be deleted. If an administrator removes an alias from the configuration, a restart removes profiles using that address. Submission binds the From header and SMTP envelope sender to the selected identity. Wildcard sender identities are disabled.

## Vacation responses

Configure an optional `ManageSieve` upstream in the gateway configuration using the same mail account. It takes `Address`, `Username`, `Password`, and optional `CAFile`. Set `Mode` to `starttls`. The gateway uses TLS with hostname verification before authenticating with SASL PLAIN.

On the mail server, enable Sieve processing at delivery and add this include to the account’s existing active Sieve script.

```sieve
require "include";
include :personal :optional "jmap-vacation";
```

Merge `include` into the existing `require` list where applicable. Put the include before rules that end delivery script processing. Keep the account’s active script and the gateway-managed `jmap-vacation` script as separate files. The gateway updates only the named managed script through ManageSieve. A file with an unrecognized format or inconsistent checksum returns an error. The backend must support the Sieve `include`, `vacation`, `date` and `relational` extensions and execute the include on the production delivery path. [Dovecot ManageSieve](https://doc.dovecot.org/2.4.1/core/config/sieve/managesieve.html)

When configured, include `urn:ietf:params:jmap:vacationresponse` in requests using `VacationResponse/get` or `VacationResponse/set`. Update the `singleton` object and optionally pass `ifInState` from Get. The default is disabled. The optional UTC window starts at `fromDate` and ends before `toDate`. Each body is limited to 12 KiB of UTF-8. The Sieve delivery plugin sends the reply and handles loop prevention, including list and automated messages and repeat senders. The generated script requests one response per sender in seven days.

## Calendar preview

Configure `CalDAV` on the primary account, an additional account, or both. Set `URL` to the HTTPS endpoint that answers the WebDAV `current-user-principal` property, plus the account’s `Username` and `Password`. An optional `CAFile` replaces system trust roots with a PEM bundle. The gateway verifies the server certificate and hostname, uses HTTP Basic authentication over TLS, and keeps DAV requests on the configured origin. Configure the canonical endpoint directly when a server normally redirects clients.

On configured accounts, the session advertises the preview capability `https://github.com/sendanor/jmap-gateway/capabilities/calendars-preview`. Include it and the JMAP Core capability in `using`. The preview supports two methods.

- `Calendar/get` reads calendar collections directly under the account’s CalDAV calendar home. It projects `id`, `name`, `description`, `color`, `sortOrder`, and `isVisible`. Color, order, and visibility use preview defaults. With more than 32 calendars, pass specific known IDs. An unfiltered request returns `requestTooLarge`.
- `Calendar/changes` reports created, updated, and destroyed collection IDs since an observed state. The gateway detects changes on requests. A display-name update preserves the JMAP ID. IDs depend on the account, CalDAV origin, and canonical collection path, so changing the collection path appears as a deletion and an addition.

The standard JMAP Calendars capability requires event, scheduling, and alert support. Its implementation is tracked in the [conformance tracker](docs/JMAP-CONFORMANCE.md). CalDAV outages, upstream credential rejection, and invalid upstream responses return `serverUnavailable`.

The black-box check uses two disposable CalDAV accounts and an additional JMAP account whose CalDAV credentials are intentionally invalid. Pass their gateway config, a fresh private checkpoint path, and the fixture's two CalDAV home paths to `scripts/verify-calendars.py`. Run the script with `before`, restart the gateway with the same state directories, then run with `after`. Stop CalDAV and run with `unavailable` to verify outage handling.

## Test coverage

Run `scripts/coverage.sh` from the checkout with Go and Bash. The command tests the module, includes the gateway executable and fails on any uncovered Go statement. It writes `.local/coverage.out`. Use `scripts/coverage.sh --report` to inspect an incomplete result.

To include a real-server acceptance run, build the gateway with `go build -cover -covermode=atomic -coverpkg=./... -o .local/jmap-gateway ./cmd/jmap-gateway`. Start it with `GOCOVERDIR` set to a fresh existing directory, run the acceptance client against that process, then stop the gateway with SIGINT or SIGTERM so it writes the counters. Set `JMAP_COVERAGE_DATA` to that directory when running `scripts/coverage.sh`. Use the same checkout and Go toolchain for both builds.

`Mailbox/set`, `Email/set`, and `EmailSubmission/set` accept `ifInState`. Simultaneous membership in multiple mailboxes and delayed submission remain open. Blob uploads are limited to 2 MiB per request and are stored under the private state directory. Unreferenced uploads are capped at 32 MiB and 4,096 files per account. When the limits are reached, the oldest uploads are evicted first. Parsing supports nested message parts and bounds the number of attached-message levels. MIME part download retains the previous representation for legacy part IDs. See the [conformance tracker](docs/JMAP-CONFORMANCE.md) for verified behavior and remaining work.

Choose one writable destination with `mailboxIds`. To mark a message as a draft, supply `keywords: {"$draft": true}`. Omitted keywords default to an empty set. A draft can be saved before it has a sender, recipients or a body. Any From or Sender address supplied at creation must be authorized for the account, and SMTP submission validates the finished message. Draft creation accepts up to 32 address entries across `to`, `cc`, and `bcc`. Use `textBody` and `htmlBody` with `bodyValues` for inline text, and `attachments` with `blobId` for files. Supply `bodyStructure` for an explicit tree in place of those three lists. Blob-backed content can reference an upload, a stored message, or a MIME part from the account. The total input blob size is limited to 1 MiB per draft and the encoded message to 2 MiB. Draft creation supports mixed, alternative, related, digest, and parallel multipart structures. Use a `blobId` and `type: "message/rfc822"` to forward a message with ASCII headers. Use `type: "message/global"` for raw UTF-8 headers. The gateway preserves transportable CRLF lines and their terminal line ending. It keeps embedded headers separate from the SMTP envelope. The forwarded part can be downloaded or passed to `Email/parse` using its returned blob ID. Run `JMAP_SCENARIO=forward-attachment` with the acceptance client and recipient verifier to check byte-identical delivery. Set `JMAP_EMBEDDED_FORMAT` to `7bit`, `8bit`, or `global`. For the negative test, disable SMTPUTF8 on the disposable relay and set `JMAP_EMBEDDED_FORMAT=global` and `JMAP_EXPECT_SMTP_UTF8_REJECTION=1`. [Message encapsulation](https://www.rfc-editor.org/rfc/rfc2046.html#section-5.2.1)

The gateway scans up to 128 listed folders and 10,000 message instances per account. API limits include a 1 MiB JSON request, 32 method calls, 32 objects per get, and 16 objects per set. MIME retrieval reads at most 2 MiB per raw message and 24 MiB of raw mail per API request. Use a property projection for metadata on larger messages. Text bodies are decoded from MIME transfer encoding and charset. Attached parts have download IDs. The gateway bounds MIME nesting and decoded size.

Content search reads from IMAP on demand. Queries using only header content can fetch up to 128 KiB of headers per candidate without fetching its body. Body, combined text, and attachment-presence filters parse MIME within the raw retrieval limits. Received-date, mailbox and size conditions in the same filter can reduce the candidates before the gateway reads their content. A read or parsing failure returns a method error so clients can distinguish it from an empty result. Text matching is case-insensitive, honors single- and double-quoted phrases, decodes encoded headers and text parts, and searches visible HTML text plus `alt` and `title` attributes. Attachment content search covers `text/*` parts. The gateway keeps decoded content in memory for the query and retains result IDs and digests for synchronization.

The account advertises the Email sort properties in RFC 8621 §4.4.2. `from` and `to` use the first address's display name, falling back to its address. `subject` uses the RFC 5256 base subject, and `sentAt` compares absolute times with missing or malformed dates first in ascending order. These sorts read the bounded IMAP header section or reuse MIME data already read for the filter. String comparators accept `i;ascii-casemap` and `i;octet`. String sorts without an explicit collation use the Unicode Collation Algorithm with case ignored and no language-specific tailoring. At equal sort keys and received dates, Email results are ordered by immutable Email ID, including after a mailbox move.

Select individual headers in `properties` for the message or in `bodyProperties` for MIME parts. For example, `header:Subject:asText:all` decodes all instances in message order, and `header:List-POST:asURLs` parses the last instance. Selectors preserve the requested property spelling, validate the form for known fields, and return `null` for a missing single header or `[]` for a missing `:all` selector. `sentAt` uses the selected Date header's offset. A request with individual message selectors and only raw headers or metadata uses the bounded IMAP header section.

`SearchSnippet/get` accepts up to 32 Email IDs and the corresponding query filter. It highlights terms from positive conditions, escapes message text before adding `<mark>` tags, and limits the rendered preview to 255 UTF-8 octets. It chooses the first matching plaintext or visible HTML body part. A field is `null` when a snippet cannot be generated for it. Missing messages appear in `notFound`. Snippets are derived on demand.

## IMAP and SMTP state

Draft creation accepts the named Email header properties and top-level `header:<name>` selectors. Use `:all` for repeated values and an allowed typed form such as `:asText`, `:asGroupedAddresses` or `:asURLs`. Raw values start immediately after the colon. Use CRLF followed by whitespace for a continuation. The gateway rejects line breaks that would create a separate header, duplicate properties for the same field, and top-level `Content-*` selectors. It verifies the configured From and Sender addresses and generates Date and Message-ID when omitted. Use `JMAP_SCENARIO=draft-headers` with the acceptance client to verify an IMAP round trip and delivery. [JMAP Mail draft creation](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.6)

MIME parts accept the same `header:` syntax. Use either a named part property or the corresponding selector, such as `type` or `header:Content-Type`. The gateway preserves supplied raw values and repeats, generates multipart boundaries and transfer encodings, and adds a UTF-8 charset when needed for text created from `bodyValues`. The outermost MIME part shares the message header block and cannot redefine a field supplied there.


Discovered mailbox IDs initially derive from the account and IMAP mailbox path. `mailboxes.json` stores IDs for gateway-created mailboxes, sort order, and path changes made through JMAP. A JMAP rename or reparent preserves IDs for the entire selectable subtree. Email IDs initially derive from the mailbox ID, UIDVALIDITY, and UID. A JMAP mailbox rename preserves Email IDs when IMAP preserves UIDVALIDITY and UID. A confirmed JMAP Email move preserves the Email, Thread, and Blob IDs using the destination locator in `email-moves.json`. Direct IMAP moves and copies and UIDVALIDITY resets can still change Email IDs. Keep both state files with the account state across restarts and backups. IMAP standard and supported custom flags map to JMAP keywords. The gateway uses `BODY.PEEK` for reads and checks UIDVALIDITY again before fetching a message or changing its flags.

For IMAP servers advertising `ACL`, the gateway reads each listed mailbox’s effective rights with `MYRIGHTS`. `Mailbox/get` exposes separate rights for seen flags, other keywords, insertion, removal, child creation, rename, deletion and posting. A mailbox with lookup access alone can remain visible with zero counts. The gateway skips it when loading messages and rejects message filters that explicitly name it. An ACL change is reflected in `Mailbox/changes`. Servers without `ACL` use the IMAP selection mode and capability checks. [JMAP MailboxRights](https://www.rfc-editor.org/rfc/rfc8621.html#section-2) · [IMAP ACL](https://www.rfc-editor.org/rfc/rfc4314.html)

The gateway requires readable UID metadata for durable Email IDs and mailbox rename recovery. It rejects an append or move when the target ACL would silently discard flags that the operation is meant to store. Removal requires both the IMAP deleted-flag and expunge rights and support for UID-scoped expunge.

To preserve Mailbox IDs across renames performed by another IMAP client, set `MailboxMetadataVendor` on the account to a registered ACAP vendor token that you control. Discovery then signs and stores a private identifier on each selectable mailbox other than INBOX. The upstream must advertise IMAP METADATA, allow the account to read and write its private annotations, and preserve them through a rename. A successful scan before an external rename binds existing JMAP IDs to their IMAP mailboxes. A rename also preserves Email IDs when the upstream preserves UIDVALIDITY and UIDs. The gateway returns `serverFail` for duplicate or invalid identifiers or a changed vendor namespace. Back up the account state, signing key and upstream annotation store together. With no vendor configured, mailbox discovery uses local IDs and tracks renames made through JMAP. [IMAP METADATA](https://www.rfc-editor.org/rfc/rfc5464.html#section-4.1) · [IANA vendor registry](https://www.iana.org/assignments/acap-registrations#acap-registrations-4)

Mailbox writes use IMAP `CREATE`, `RENAME`, `SUBSCRIBE`, `UNSUBSCRIBE`, and `DELETE`. The gateway protects INBOX and the configured Drafts path from rename or removal. Special-use creation depends on IMAP `CREATE-SPECIAL-USE`, and existing role changes are restricted. The gateway checks UIDVALIDITY before deletion and checks message count when the client hasn't opted to remove messages. IMAP has separate `STATUS` and `DELETE` commands, so an independent IMAP writer can still add a message between the empty-mailbox check and deletion. A pending rename is checked against the old and new paths and known UIDVALIDITY values on the next scan. If the gateway cannot establish the outcome, mailbox operations return `serverFail` until the conflict is resolved. IMAP permissions still govern which commands succeed.

`Email/set` accepts a full `keywords` object or `keywords/<keyword>` patch paths with `true` to add and `null` to remove. It normalizes keyword names to lowercase and supports JSON Pointer escapes. Mixed patches and full replacements read the current IMAP flags before writing the resulting set. An independent writer can modify flags between that read and the write. `Email/set` destroys an Email only when IMAP supports `UIDPLUS` or IMAP4rev2. It applies `\Deleted` and expunges the selected UID after checking UIDVALIDITY. Messages flagged `\Deleted` are excluded from JMAP results and mailbox counts. A definite expunge rejection triggers an attempt to remove a deletion flag written by this request. Some upstream failures can leave the flag set.

An Email move accepts a full one-entry `mailboxIds` object or a patch that removes the original membership and adds the destination. It requires native `UID MOVE` and a valid `COPYUID` response. A request that changes both the mailbox and keywords returns `forbidden` because those are separate IMAP transactions. The gateway records an intent before sending `MOVE`. If the acknowledgement is lost, an unchanged source and destination UID sequence allows it to clear that intent. An unresolved outcome makes mail snapshots temporarily unavailable and requires reconciliation. A confirmed mapping whose disk write failed is retained for another write attempt while the gateway process stays alive.

Threads use the first usable identifier in `References`, `In-Reply-To`, or `Message-ID`, together with the normalized subject and the account. This permits a reply to establish its thread before the original appears. The gateway fetches up to 8 KiB of selected IMAP headers per message. Messages without usable headers receive individual threads. The gateway keeps existing threads separate if a later message provides only an indirect link between them. Unread thread counts include related mail in other folders, with trash counted independently. Clients that tried earlier builds with synthetic thread IDs should refresh their Email and Thread caches after upgrading.

The gateway snapshots mail metadata once per API request, carries its own mutations into that snapshot, and advances the state token when it observes a data change. The next request picks up upstream changes. Concurrent changes from other IMAP clients can occur during a scan. `ifInState` compares against the observed snapshot and does not lock out external IMAP clients.

Synchronization history lives in the private state directory. It records IDs, digests and mailbox counts. Each record type retains up to 1,024 observed transitions and 50,000 reverse changes, subject to these capacity limits. Clients whose state has fallen outside the window receive `cannotCalculateChanges` and can reload that record type. Use `maxChanges` at or below the advertised get limit to fetch each batch in one follow-up request. Pages finish their original change window before advancing to newly observed changes. The server signs intermediate state tokens with a separate key in `changes.key`. Keep this file and the history files with the account state across restarts. A write failure keeps synchronization available in memory and retries persistence on the next observation.

Query synchronization uses `query-history.json` and the same signing key. It retains up to 128 recently used result snapshots and 50,000 total result rows. Query states bind to the account, type, filters, sort order, mailbox tree options and the `collapseThreads` option. A client can request a total, limit changes with `maxChanges`, and use `upToId` for a query with immutable filters and sort properties. If surviving rows crossed that anchor between the cached and current order, the gateway computes the complete delta and applies the same `maxChanges` bound. Reissue the original query if the gateway returns `cannotCalculateChanges` for an expired or mismatched state or `tooManyChanges` for a delta above the requested limit.

The gateway can submit a stored Email from a readable IMAP mailbox when its From address matches the configured identity. Before SMTP it reserves the submission in a durable, exclusively locked ledger, using the SHA-256 digest of the stored bytes. The Email ID also matches replays, including after the Email is removed. Identical bytes under a new mailbox UID resolve to the same reservation. A replay with different explicit recipients returns an envelope error. The gateway still reads older reservations keyed by its generated Message-ID. A positive DATA reply records acceptance. A definite rejection or pre-DATA connection failure releases the reservation. A lost final DATA reply leaves the message blocked. The ledger stores envelope addresses, digests, and outcome metadata.

Submission accepts up to 32 ASCII envelope recipients. Supply `envelope` with the configured identity as `mailFrom` and the desired `rcptTo` list, or let the gateway derive recipients from To, Cc, and Bcc. Derived recipients are deduplicated, respecting local-part case. The gateway removes Bcc from the SMTP copy and keeps it in the stored Email. Client-supplied ESMTP parameters remain unsupported. An SMTP recipient rejection prevents DATA for the entire submission. Permanent rejections list the invalid recipients. A temporary rejection returns a retryable upstream error. A positive SMTP SIZE limit below the message size returns `tooLarge` with `maxSize`.

Use `onSuccessUpdateEmail` to file an accepted draft and clear its `$draft` keyword, or `onSuccessDestroyEmail` to remove its Email. Reference a newly created submission as `#<creationId>`. The gateway runs one implicit `Email/set` for the matched successful items and returns that response under the submission call’s tag. A filing error leaves SMTP acceptance recorded. A combined move and keyword update can leave the Email in the destination if IMAP confirms MOVE and then rejects STORE. The Email retains its ID, so a client can read the current flags and retry the update.

An accepted submission has `undoStatus: "final"`. `EmailSubmission/set` accepts patches that preserve its current properties. A successful creation, update, or destruction can trigger the requested `onSuccessUpdateEmail` or `onSuccessDestroyEmail` action in a separate implicit `Email/set` response. Use `destroy` to remove a submission from client history. The removal appears in `EmailSubmission/changes` and `EmailSubmission/queryChanges`. The private ledger retains the acceptance reservation to prevent another SMTP delivery of the same Email. A create retry for a removed submission returns `forbiddenToSend`. Run `scripts/acceptance.mjs` with `JMAP_SCENARIO=destroy-submission` and the gateway acceptance settings to exercise this flow. [JMAP Mail submission](https://www.rfc-editor.org/rfc/rfc8621.html#section-7.5)

The gateway negotiates `8BITMIME` for raw 8-bit wire data and `SMTPUTF8` for UTF-8 envelope addresses or raw UTF-8 headers, including headers in attached messages. It derives the MAIL parameters from the message it will transmit. If the relay lacks a required extension, the gateway returns `forbiddenToSend` before opening a transaction and releases the submission reservation. The configured relay must support these extensions for the corresponding content. SMTP envelope addresses support ASCII and UTF-8 dot-atom local parts and IDNA domains. Sender authorization matches the configured address exactly. Derived recipients with equivalent Unicode or ASCII domain labels are deduplicated while local parts retain their original bytes and case. [8BITMIME](https://www.rfc-editor.org/rfc/rfc6152.html) · [SMTPUTF8](https://www.rfc-editor.org/rfc/rfc6531.html)

Set `"SMTPDeliveryNotifications": true` on an account whose SMTP relay advertises DSN after TLS negotiation. The account advertises `DSN` in `submissionExtensions`. In an explicit envelope, use `RET` and `ENVID` for MAIL FROM, and `NOTIFY` and `ORCPT` per recipient. Supply decoded JSON strings. The gateway applies xtext on the SMTP wire and returns the decoded values through `EmailSubmission/get`. `ORCPT` supports `rfc822` with the same ASCII address as the envelope recipient. If the relay lacks DSN, the gateway rejects the submission before MAIL FROM and releases its reservation for a safe retry. [JMAP submission](https://www.rfc-editor.org/rfc/rfc8621.html#section-7) · [SMTP DSN](https://www.rfc-editor.org/rfc/rfc3461.html)

Set `SMTPDeliveryReportMailbox` to the exact IMAP path of a dedicated report folder. Route only authoritative reports from your SMTP infrastructure into this folder. Give the configured IMAP user lookup and read access while withholding insert and rename rights, and restrict alternate write routes and access to the parent path. Keep the folder out of ordinary inbound mail routing. A mailbox's ACL alone cannot establish the origin of a message placed there.

For submissions with explicit DSN options, the gateway generates the effective `ENVID` and returns it in the JMAP envelope. It matches reports against that identifier and the original envelope recipient, or the final recipient when the original is absent. A delivered or failed report changes the recipient’s `delivered` value to `yes` or `no`. The first final outcome takes precedence. Nonfinal reports leave the delivery value unchanged. The gateway lists matching reports in `dsnBlobIds` even when they are nonfinal. Retain the messages in the source IMAP folder to keep those blobs downloadable. If the report folder is unavailable, the last recorded status remains visible. [Delivery Status Notifications](https://www.rfc-editor.org/rfc/rfc3464.html#section-2)

SMTP acceptance means the submission server took responsibility for the message. At acceptance, `deliveryStatus` records the authenticated relay’s RCPT TO reply per recipient and returns `unknown` for delivery and display. A correlated final report can update the delivery result and supply its own SMTP diagnostic. Older submission records can return `null`. After a lost HTTP reply, use the existing Email ID to replay the submission. Repeating draft creation generates a new Message-ID and can lead to a second delivery. For a blocked message, reconcile the available Message-ID or other message details against the SMTP queue, logs, or recipient inbox before deciding how to proceed. Keep the ledger across restarts and restores. IMAP APPEND can also finish after the client loses the reply. Rescan the destination mailbox before trying a creation or import again.

## EventSource

Discover `eventSourceUrl` in the session, substitute `types`, `closeafter` and `ping`, and use the normal Bearer header. Subscribe with `types=*` or a comma-separated list of types. The gateway sends `state` events with current JMAP state strings and accepts `Last-Event-ID` on reconnect. The signed cursor remembers the types delivered on the stream. If a client reconnects with additional types, it receives their current states. Use the relevant Get or Changes method to synchronize records.

While streams are connected, shared snapshots observe IMAP and configured ManageSieve changes at approximately two-second intervals. Notifications can coalesce changes made between observations. A stream can remain open with `closeafter=no` or finish after the first state event with `closeafter=state`. Heartbeats are disabled with `ping=0` and capped at 300 seconds when enabled. The gateway accepts four simultaneous streams per account. Preserve streaming responses through HTTP proxies.

To receive delivery-only notifications, use `types=EmailDelivery` for EventSource or `["EmailDelivery"]` for an HTTPS push subscription. The gateway persists this state with the Email change history. It advances when an IMAP observation finds a new Email, including an imported or newly composed message. Flag changes, deletions and gateway-tracked moves preserve it. Use your cached Email state with `Email/changes` to retrieve new records. Direct IMAP moves can produce a new Email ID and appear as additions. [JMAP Mail push types](https://www.rfc-editor.org/rfc/rfc8621.html#section-1.5)

## HTTP push subscriptions

Set `PushOrigins` to the HTTPS origins administered for push delivery, for example `["https://push.example.org"]`. The gateway accepts subscription URLs on those origins and verifies the receiver’s certificate and hostname. Set `PushCAFile` only if the receiver uses a private CA. Requests follow no redirects and omit the JMAP bearer token. An empty allowlist leaves HTTP push registration disabled.

Create a subscription with `PushSubscription/set`, then return the code received in the `PushVerification` POST using an update to that subscription. The gateway sends state changes only after confirmation and filters them by the requested `types`. When the subscription supplies `keys`, it encrypts verification and state notifications with Web Push `aes128gcm`. The default and maximum lifetime is seven days. HTTP 429 delays delivery according to `Retry-After` with a minimum of 15 seconds, and changes accumulate during the delay. Verification is attempted once per creation, with eight subscriptions and twelve verification attempts per minute per credential.

Subscriptions and acknowledged states survive gateway restart. Changing the configured bearer token revokes existing subscriptions when the gateway next starts. Get responses omit subscription URLs and encryption keys. Destroyed and expired records are removed from the active private state file. [JMAP push subscriptions](https://www.rfc-editor.org/rfc/rfc8620.html#section-7.2) · [Web Push encryption](https://www.rfc-editor.org/rfc/rfc8291.html)

```sh
  JMAP_RECIPIENT=qa@example.test node scripts/acceptance.mjs

# Export JMAP_TOKEN using the token from the private gateway configuration.
export JMAP_SESSION_URL=https://jmap.example.org/.well-known/jmap
export JMAP_RECIPIENT=controlled-recipient@example.org
node scripts/acceptance.mjs
```
